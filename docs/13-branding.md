# 13. Брендбук СберМобайл и оформление интерфейса

## 13.1. Что даёт брендбук и чего он не даёт

ТЗ ссылается на брендбук СберМобайл в Figma:

```
https://www.figma.com/design/Q2lrTU85ohdbpBQIOe48KW/SberMobile_guide?node-id=1-8253
```

Формально критерии оценки не содержат пункта «соответствие фирменному стилю»: требование к интерфейсу — «понятный и однозначный результат», «отсутствие неоднозначных формулировок», «понятен без дополнительного обучения». Однако ссылка приведена в ТЗ намеренно, и решение, визуально узнаваемое как продукт СберМобайл, при демонстрации воспринимается как готовое к встраиванию, а не как прототип. Это косвенно поддерживает и критерий К4.

Поэтому подход такой: **интерфейс проектируется независимо от доступа к брендбуку, а фирменный стиль применяется как заменяемый слой.**

## 13.2. Слой токенов дизайна

**Реализовано этапом 6.1, значения шкал переведены в `rem` этапом 6.2.** Пакет `packages/ui-tokens` существует: объект токенов `designTokens` (`src/tokens.ts`) типизирован интерфейсом `DesignTokens` (`src/types.ts`) и содержит ровно шесть групп таблицы ниже; `generateCssVariablesText`/`generateCssVariablesBlock` (`src/css-variables.ts`) превращают дерево токенов в строку CSS-переменных с префиксом `--esim-` для вставки в теневой DOM виджета (§13.1 — «Пригодность к встраиванию») либо в `:root` демонстрационного приложения. Значения — нейтральная плейсхолдер-палитра (не брендированная), доступа к брендбуку не получено (см. §13.3, ADR-038): значения подставляются в этот файл будущим агентом одной правкой, без изменения типов, разметки или логики. Этап 6.2 (ADR-039) перевёл `typography.fontSize`/`spacing`/`shape.radius.{sm,md,lg}` из `px` в `rem` — требование §13.4 «корректная работа при увеличенном системном шрифте» иначе не выполнялось бы буквально; толщина границ, тени и радиус `full` (геометрия штриха/пилюли) осознанно остались в `px`. Правка значений, без изменения структуры типов — тест уникальности значений внутри шкалы (`tokens.spec.ts`) не потребовал изменений. Контраст пар «текст на фоне» проверяется тестом по формуле WCAG (`src/contrast.ts`, `src/accessibility.spec.ts`) — требование §13.4 «контраст не ниже AA» тем самым выполнено проверяемо, а не декларативно.

Все визуальные значения выносятся в один файл токенов (`packages/ui-tokens`), из которого генерируются CSS-переменные:

| Группа токенов | Состав                                                                                                                                        |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Цвета          | Основной, вторичный, фон, поверхность, текст (основной, вторичный, инверсный), границы, состояния (успех, предупреждение, ошибка, информация) |
| Типографика    | Гарнитура, шкала кеглей, интерлиньяж, насыщенность, регистровые правила заголовков                                                            |
| Отступы        | Шкала отступов и внутренних полей                                                                                                             |
| Формы          | Радиусы скругления, толщина границ, тени                                                                                                      |
| Состояния      | Наведение, нажатие, фокус, недоступность, загрузка                                                                                            |
| Компоненты     | Кнопки (основная, вторичная, текстовая), поле ввода с подсказками, элемент списка выбора, карточка результата, индикатор загрузки             |

Замена оформления на фирменное — правка значений в одном файле, без изменения разметки и логики. Это зафиксировано как ADR-012.

Для трёх статусов результата в брендбуке потребуются: цвет и иконка успеха (поддерживает), цвет и иконка отказа (не поддерживает), цвет и иконка нейтрального/информационного состояния (требуется уточнение). Важно, чтобы «не поддерживает» не выглядело как сообщение об ошибке приложения: это корректный результат, а не сбой.

## 13.3. Что нужно для работы с Figma

**Проверено этапом 6.1: доступ так и не появился.** В рабочем окружении по-прежнему настроены серверы MCP для Context7, Playwright и Prisma — сервера MCP для Figma нет, переменная `FIGMA_TOKEN` не задана. Агент 6.1 не стал ждать доступа (это заблокировало бы весь объём этапа интерфейса) и заполнил `packages/ui-tokens` нейтральной палитрой — решение зафиксировано ADR-038, оно не отменяет ни один из вариантов ниже: как только доступ появится, значения токенов заменяются правкой `packages/ui-tokens/src/tokens.ts` без изменения типов и компонентов. Ниже — варианты по возрастанию требований, актуальные для того агента, который получит доступ.

### Вариант А. Токен доступа Figma REST API (рекомендуемый, без установки MCP)

Самый простой путь. Достаточно личного токена доступа Figma от учётной записи, которая может открыть файл по ссылке.

1. Figma → Settings → Security → Personal access tokens → создать токен со правами чтения содержимого файлов (`file_content:read`, дополнительно `file_dev_resources:read`).
2. Передать токен через переменную окружения (не в текст переписки и не в репозиторий):

```bash
export FIGMA_TOKEN="figd_..."
```

После этого я смогу получить структуру нужного узла брендбука, перечень стилей (цвета, текстовые стили) и выгрузить изображения фреймов:

```bash
# файл: Q2lrTU85ohdbpBQIOe48KW, узел из ссылки: 1-8253 → 1:8253
curl -s -H "X-Figma-Token: $FIGMA_TOKEN" \
  "https://api.figma.com/v1/files/Q2lrTU85ohdbpBQIOe48KW/nodes?ids=1:8253"
curl -s -H "X-Figma-Token: $FIGMA_TOKEN" \
  "https://api.figma.com/v1/files/Q2lrTU85ohdbpBQIOe48KW/styles"
```

Ограничение: токен даёт доступ только к тем файлам, которые доступны его владельцу. Если ссылка из ТЗ открывается у вас в браузере — токен подойдёт.

### Вариант Б. Сервер MCP для Figma

Даёт более удобную работу с макетами (получение кода компонента, скриншотов узлов, переменных дизайна).

- **Удалённый сервер Figma:** добавить в конфигурацию MCP адрес `https://mcp.figma.com/mcp`, авторизация через OAuth в браузере.
- **Локальный сервер в приложении Figma:** в настольном приложении Figma включить Dev Mode MCP Server, после чего сервер доступен по адресу `http://127.0.0.1:3845/mcp`.

Требования: учётная запись Figma с доступом к файлу; для инструментов режима разработчика нужен соответствующий тип места в тарифе Figma (Dev или Full на платном плане). Если такого места нет, вариант А остаётся работоспособным.

Готов подготовить фрагмент конфигурации MCP для добавления в проект, если выберете этот вариант.

### Вариант В. Выгрузка вручную

Если доступ к API и MCP получить не удаётся, достаточно любого из перечисленного:

- экспорт нужных фреймов брендбука в PNG или PDF (я прочитаю изображения и сниму с них значения);
- выгрузка переменных дизайна или стилей из Figma в JSON;
- просто перечень значений: основные цвета в HEX, названия гарнитур, шкала кеглей, радиусы скругления.

Практически этого достаточно: для нашего интерфейса нужны около двадцати значений, а не весь брендбук.

**Итоговый статус на конец этапа интерфейса (агент 6.6, docs/09-decisions.md ADR-042).** Доступ к брендбуку не появился ни на одном из шагов 6.1–6.6: MCP-сервер Figma не подключён, `FIGMA_TOKEN` не задан, ни файл, ни перечень значений вручную не поступили. Все шесть шагов интерфейса (клиент API, компоненты, Web Component, демонстрационный контур, e2e-тесты, эталонная выборка сигналов) реализованы и проверены на нейтральной палитре `packages/ui-tokens` без единой блокировки от отсутствия доступа — это подтверждает саму идею заменяемого слоя (§13.1, ADR-012). Подстановка фирменных значений остаётся правкой ровно одного файла — `packages/ui-tokens/src/tokens.ts` (шкалы в `rem`, тест уникальности значений и тест контраста AA, §13.2, не требуют изменений при замене значений на другие, лишь бы новые пары «текст/фон» проходили ту же формулу WCAG). Получение доступа и сама подстановка фирменных значений остаются открытой задачей, не привязанной к конкретному агенту цепочки 1–8 — любой следующий агент, получивший доступ, может выполнить её без согласования архитектуры.

## 13.4. Требования к интерфейсу, не зависящие от брендбука

Эти требования выполняются независимо от доступа к фирменному стилю и напрямую влияют на оценку.

| Требование                            | Реализация                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Однозначность результата              | Ровно три состояния результата, единая формулировка для каждого, отсутствие промежуточных трактовок                                                                                                                                                                                                                                                  |
| Понятность без обучения               | Один экран, один основной элемент действия, результат в заголовке, а не в подписи                                                                                                                                                                                                                                                                    |
| Отсутствие неоднозначных формулировок | Тексты проверяются по контрольному списку: без слов «возможно», «вероятно», «скорее всего» в статусе результата                                                                                                                                                                                                                                      |
| Уточнение не выглядит ошибкой         | Нейтральное оформление, формулировка «нужно уточнить», а не «не удалось определить»; всегда предлагается следующий шаг                                                                                                                                                                                                                               |
| Только русский язык                   | Все тексты в ресурсах на русском языке; проверка отсутствия иноязычных строк в интерфейсе — автоматическая                                                                                                                                                                                                                                           |
| Доступность                           | Работа с клавиатуры, разметка для экранного диктора, контраст не ниже AA, корректная работа при увеличенном системном шрифте. Домашняя страница и `/debug` на узком экране (телефон): без горизонтальной прокрутки страницы, поля ввода не меньше `1rem`, кнопки на всю ширину, отступы с `safe-area`. Раздел `/admin` на телефон не рассчитывается. |
| Соответствие каналу                   | Виджет не навязывает страницу-обёртку, наследует ширину контейнера, не блокирует прокрутку                                                                                                                                                                                                                                                           |

## 13.5. Финальные пользовательские формулировки — на утверждение пользователем

**Статус: черновик снят, ниже — финальный список, требующий утверждения пользователем одним проходом (ADR-025, вопрос 7; docs/09-decisions.md).** Формулировки предлагает агент, пользователь либо утверждает список целиком, либо возвращает с конкретными правками — по решению вопроса 7 итеративное согласование по одной фразе не предполагается. Тексты видны пользователю сервиса и напрямую оцениваются комиссией («интерфейс результата не должен содержать неоднозначных формулировок», §13.4 ниже) — поэтому приведены не намерения, а текст, уже действующий в коде (`apps/api/src/common/response/presentation.ts`, блок `presentation` ответа API, ADR-010, docs/06-api-contract.md §6.2): так исключается зазор между тем, что видит комиссия, и тем, что утверждает пользователь.

Тексты приведены в ответе API в блоке `presentation`, поэтому заказчик получает согласованные формулировки даже при использовании только API, без нашего интерфейса или виджета.

| Элемент    | Текст                                                                                      | Условие показа                                    |
| ---------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------- |

Оформление нейтральное, без цвета и формулировок, характерных для сообщения об ошибке (§13.2 выше) — «не поддерживает» является корректным результатом определения, а не сбоем сервиса. Отдельное коммерческое действие («подобрать альтернативную SIM-карту» и подобное) в текущем объёме не реализуется: это отдельный сценарий продажи, не описанный ни одним ADR и не входящий в API-контракт (docs/06); переход к ручному поиску уже даёт пользователю следующий шаг, что закрывает требование §13.4 «всегда предлагается следующий шаг» без домысливания несуществующего сценария.

| Пояснение | «Не удалось однозначно определить статус eSIM для вашего устройства. Уточните модель.» | Готового вопроса нет (кандидаты расходятся, устройство не опознано и т. п.) |

Оформление нейтральное/информационное (§13.2 выше) — уточнение не должно выглядеть как ошибка приложения.

### Правила, общие для всех трёх статусов

Проверены по контрольному списку §13.4 ниже: ни один текст выше не содержит слов «возможно», «вероятно», «скорее всего» или иных смягчающих оценочных конструкций (проверка вынесена в тест `apps/api/src/common/response/presentation.spec.ts`); заголовок несёт результат, пояснение — контекст, что соответствует требованию «понятность без обучения» (результат в заголовке, а не в подписи).

### Что явно вне утверждаемого списка

Тексты интерфейса, не входящие в блок `presentation` API (подписи полей формы, состояния загрузки, сообщения об ошибке сети, тексты раздела `/admin`), в объём этого решения не входят — они не видны комиссии напрямую тем же образом, что три статуса результата, и будут утверждены агентом 6 при сборке интерфейса тем же порядком (агент предлагает, пользователь утверждает одним проходом, ADR-025).

**Реализовано этапом 6.4** (`apps/web/src/debug/`, docs/07-integration.md §7.6, docs/03-detection-algorithm.md §3.10, ADR-041): тексты выше перенесены дословно; технические подписи полей, не входящие в этот список буквально (`requestId`, поля формы экспорта записи, предупреждение о необходимости ручной проверки `expected`), заведены минимально и нейтрально этим агентом — список выше их не покрывает, а §13.6 явно оставляет обвязку этого экрана следующему агенту (см. абзац выше). Подсказка категории эталонной выборки («Предложено по сигналам: … Можно сменить.») — такая же техническая обвязка, не часть утверждённой таблицы.

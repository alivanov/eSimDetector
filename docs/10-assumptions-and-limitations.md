# 10. Допущения и ограничения

Раздел является обязательным по критерию К3 («описание ограничений решения»). Ограничения перечислены полно и без смягчений: часть из них — свойства веб-платформы, которые невозможно устранить в рамках любого браузерного решения, и открытое их изложение мы считаем сильной стороной, а не слабой.

## 10.1. Допущения

| № | Допущение | Основание | Что произойдёт, если допущение неверно |
|---|---|---|---|
| Д-1 | Целевая аудитория — пользователи мобильных браузеров на территории РФ | Сервис встраивается в каналы самообслуживания СберМобайл | Изменится приоритет наполнения справочника; логика не изменится |
| Д-2 | Основные браузеры — Chrome, Safari, Яндекс.Браузер, Samsung Internet, а также WebView в приложениях | Структура рынка мобильных браузеров в РФ | Возможен рост доли уточнений в неучтённых браузерах |
| Д-3 | Устройство пользователя приобретено для рынка РФ, если не указано иное | Наиболее вероятный случай | Для моделей с региональными различиями сервис задаёт уточняющий вопрос, поэтому ошибки не возникает |
| Д-4 | Вопрос пользователя — о технической поддержке eSIM устройством, а не о готовности тарифа или статусе абонента | Формулировка ТЗ | Потребуется интеграция с системами заказчика следующим шагом сценария |
| Д-5 | Интерфейс требуется только на русском языке | Прямое указание | Понадобится слой локализации; тексты уже вынесены в отдельные ресурсы, поэтому изменение локальное |
| Д-6 | Справочник устройств поддерживается в актуальном состоянии | Данные вынесены из кода, обновление не требует правки кода | Новые модели будут уходить в уточнение — деградация мягкая, без ложных ответов |
| Д-7 | Заказчик встраивает виджет скриптом на страницу, а не через iframe с другого домена | Рекомендация по умолчанию | При iframe без делегирования Client Hints точность на Android снизится; предупреждение вынесено в инструкцию по подключению |
| Д-8 | Демонстрационный контур запускается в среде с Docker | Требование к результату | Предусмотрен вариант локального запуска без Docker, кроме базы данных |
| Д-9 | Достаточная точность по iPhone достигается определением группы моделей, а не точной модели | ADR-002 | Если комиссия ожидает точное название модели iPhone, ни одно браузерное решение не сможет его дать; ограничение изложено в 10.2 |

## 10.2. Ограничения, обусловленные веб-платформой

Эти ограничения невозможно устранить, оставаясь в браузере. Указаны меры смягчения.

### О-1. Точная модель iPhone неопределима

Safari на iOS не сообщает модель устройства и не поддерживает User-Agent Client Hints. Определение по геометрии экрана даёт группу моделей, а не одну модель.

*Смягчение:* определяется статус eSIM, а не модель (ADR-002); при неоднозначности статуса — выбор из 2–5 моделей одним тапом. Практически на iOS 17 и новее статус определяется однозначно.

### О-2. Модель Android-устройства доступна только через User-Agent Client Hints

Строка User-Agent в Chrome фиксирована значением `Android 10; K`. Модель приходит только в высокоэнтропийной подсказке `Sec-CH-UA-Model`, которая недоступна в браузерах на движке Gecko (Firefox), в старых версиях WebView и может быть отключена настройками приватности.

*Смягчение:* деградация к разбору устаревшего формата User-Agent (в Firefox для Android модель присутствует); при полной недоступности — сценарий уточнения.

### О-3. Региональная версия устройства неотличима

Версии iPhone для рынка КНР с двумя физическими SIM не имеют eSIM, но для браузера идентичны прочим. Аналогично различаются прошивки ряда моделей Samsung.

*Смягчение:* признак `conditional` и один адресный уточняющий вопрос (ADR-007).

### О-4. Фактическое состояние устройства не проверяется

Сервис отвечает о модели, а не о конкретном экземпляре. Не проверяются: наличие eSIM в установленной прошивке, блокировка под другого оператора, исчерпание слотов для профилей eSIM, ограничения корпоративной политики управления устройством.

*Смягчение:* в сценарии уточнения даётся краткая инструкция, где в настройках устройства убедиться в наличии eSIM; результат сервиса передаётся в системы заказчика для дальнейших проверок.

### О-5. Сигналы могут быть подменены

Пользователь может изменить строку User-Agent, включить режим «запрос версии для компьютера» или использовать браузер с защитой от отслеживания, искажающей сигналы.

*Смягчение:* перекрёстная проверка сигналов между собой и с заголовками запроса, обнаружение характерных признаков эмуляции; при выявлении несогласованности — уточнение вместо ответа. Полная защита невозможна, но мотивация пользователя обманывать сервис, отвечающий на его же вопрос, отсутствует.

### О-6. Часть сигналов ограничена политиками браузера

Доступ к строке рендерера WebGL может быть закрыт, `deviceMemory` отсутствует в Safari, в приватном режиме и при усиленной защите от отслеживания набор доступных сигналов сокращается.

*Смягчение:* алгоритм работает с любым подмножеством сигналов, понижая уверенность; отсутствие сигнала снижает долю автоответов, но не приводит к ошибке.

## 10.3. Ограничения данных

### О-7. Отсутствие авторитетного открытого справочника

Публично загружаемого перечня eSIM-совместимых устройств не существует: база GSMA eSIM Compliance доступна только членам GSMA, данные GSMA Device Database распространяются коммерчески. Справочник составляется нами.

*Смягчение:* каждая запись содержит источник, дату проверки и признак достоверности; непроверенные записи не дают однозначного ответа; предусмотрена контрольная выборка фактов для сверки справочника в CI; предусмотрен адаптер для подключения коммерческого источника данных при появлении доступа.

### О-7а. Первичные данные получены от языковой модели

Первичное наполнение справочника формируется CSV-выгрузкой сторонней языковой модели. Такие данные правдоподобны, но не проверены: типичны выдуманные сервисные коды моделей, ошибки в статусе eSIM у редких устройств и ссылки на несуществующие страницы вендоров. Это самое существенное ограничение решения по критерию К1, и оно относится к данным, а не к алгоритму.

*Смягчение:* выгрузка трактуется как набор кандидатов, а не как справочник (ADR-013). Между выгрузкой и ответом пользователю стоит конвейер валидации с отбраковкой в карантин, сверка с эталонной выборкой подтверждённых вручную фактов, консенсус независимых выгрузок и тарификация достоверности; записи уровня `unverified` статус eSIM не дают. Доля расхождений с эталоном вычисляется кодом и публикуется в отчёте об импорте, поэтому качество данных не заявляется, а измеряется. Для Apple и Google Pixel применяются проверенные вручную детерминированные правила, имеющие приоритет над выгрузкой. Подробно — [14-catalog-ingestion.md](./14-catalog-ingestion.md).

*Остаточный риск:* устройство, по которому все источники согласованно ошибаются и которое отсутствует в эталонной выборке, получит неверный статус. Полностью устранить этот риск можно только заменой первичного источника данных на авторитетный.

### О-8. Полнота справочника ограничена

Устройств без eSIM существенно больше, чем устройств с eSIM. Обеспечить явную запись для каждой из них невозможно.

*Смягчение:* комбинация явных записей для распространённых моделей и правил уровня семейства; вывод по правилу помечается пониженной уверенностью; неопознанные модели попадают в очередь пополнения.

### О-9. Данные устаревают

Выходят новые модели, меняются диапазоны поддерживаемых версий ОС, изменяются региональные политики вендоров.

*Смягчение:* знания вынесены в данные; обновление не требует изменения кода и выпуска новой версии сервиса; версия справочника доступна через API.

## 10.5. Обработка персональных данных

Сервис не собирает и не хранит персональных данных. Собираемые сигналы описывают класс устройства, а не пользователя. В журнале резолюций хранится хеш сигнатуры сигналов, а не их исходные значения — это исключает использование журнала для отслеживания пользователей. Срок хранения журнала ограничен TTL-индексом и настраивается. Файлы cookie для работы сервиса не требуются.

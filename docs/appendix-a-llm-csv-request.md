# Приложение А. Запрос справочника у сторонней языковой модели

Приложение содержит готовые формулировки запросов и схему столбцов. Обработка полученных файлов описана в [14-catalog-ingestion.md](./14-catalog-ingestion.md).

## А.1. Правила, повышающие качество выгрузки

Формулировки ниже составлены с учётом того, как языковые модели ошибаются на задачах такого типа. Четыре правила дают наибольший эффект:

1. **Разрешить ответ «не знаю».** Модель, которой запрещено угадывать и разрешено писать `unknown`, выдаёт заметно меньше ложных утверждений. Пробелы дешевле закрыть модерацией, чем найти и исправить правдоподобную ошибку.
2. **Запретить выдумывать сервисные коды и ссылки.** Это два поля, которые модели выдумывают чаще всего, и одновременно два поля, ошибки в которых наиболее вредны: неверный код ломает автоопределение, а несуществующая ссылка создаёт видимость проверенности данных.
3. **Дробить на партии по 40–60 строк.** Длинные ответы обрываются, а качество деградирует к концу перечня. Разбивка по брендам и линейкам также упрощает последующую сверку.
4. **Запросить выгрузку у двух-трёх разных моделей независимо.** Совпадение независимых источников используется конвейером как подтверждение, расхождение — как повод для модерации. Это самый дешёвый доступный нам способ повысить достоверность данных. Модели берутся от разных разработчиков: две версии одной модели дают согласие, которое подтверждением не является.
5. **Выключить веб-поиск.** С поиском модели читают одни и те же страницы, и их согласие перестаёт быть независимым подтверждением. Побочный эффект — пустой `source_url` — безобиден: проверка `SOURCE_MISSING` и так ограничивает выгрузку уровнем `derived`.
6. **Проверить модель на одной партии до массового прогона.** Пригодность источника определяется не качеством знаний о устройствах, а способностью выдержать схему из 16 столбцов на нескольких десятках строк. Модель, которая её не держит, отбраковывается целиком: восстанавливать разъехавшиеся столбцы — значит угадывать, что она имела в виду. Результат такой проверки — [§А.8](#а8-результат-пилотного-прогона).

Дополнительно: не просите у модели русские написания и псевдонимы — они генерируются нашим кодом по детерминированным правилам транслитерации. Не просите Apple и Google Pixel в приоритетном порядке: перечни короткие, правила простые, они входят в курируемое ядро и проверяются вручную.

Кодировка UTF-8, разделитель — запятая, значения с запятыми в двойных кавычках, первая строка — заголовок с ровно такими именами столбцов.

| ------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `brand`             | да         | Латиницей: `Apple`, `Samsung`, `Xiaomi`, `Honor`, `Huawei`, `Google`, `realme`, `OPPO`, `OnePlus`, `vivo`, `Tecno`, `Infinix`, `ZTE`, `Nothing`, `Motorola`, `ASUS`, `Sony` | Только бренд, без названия модели                                                                          |
| `marketing_name`    | да         | Официальное название без бренда: `Galaxy S24 Ultra`, `iPhone 15 Pro`, `Redmi Note 13 Pro+ 5G`                                                                               | Без объёма памяти и цвета                                                                                  |

| `device_type`       | да         | `phone`, `tablet`, `watch`, `laptop`, `other`                                                                                                                               |                                                                                                            |

## А.3. Схема `families.csv`

Правила уровня линейки для длинного хвоста бюджетных устройств, которые нецелесообразно перечислять поштучно.

По ADR-021 эта выгрузка у языковых моделей не запрашивается: типичный статус линейки вычисляется агрегацией уже принятых записей. Схема и формулировка запроса (§А.5) сохраняются как резерв на случай линейки, по которой записей нет вовсе.

| Столбец        | Обязателен | Пояснение                                                     |
| -------------- | ---------- | ------------------------------------------------------------- |
| `brand`        | да         | Как в `devices.csv`                                           |
| `family`       | да         | Линейка: `Redmi A`, `Galaxy A0x`, `Redmi Note`, `Galaxy M`    |
| `years_from`   | да         | Год начала линейки                                            |
| `years_to`     | нет        | Год окончания, пусто для актуальных                           |
| `esim_default` | да         | `yes`, `no`, `mixed`, `unknown` — типичный статус для линейки |
| `exceptions`   | нет        | Модели-исключения через `\|`                                  |
| `confidence`   | да         | `high`, `medium`, `low`                                       |
| `notes`        | нет        | Пояснение                                                     |

Правила линейки используются для распознавания устройства и сужения набора кандидатов; самостоятельно давать отрицательный ответ они начинают только после подтверждения модератором.

## А.4. Текст запроса для `devices.csv`

Ниже — готовый текст. Подставьте партию из перечня в А.6 в место, отмеченное как `ПАРТИЯ`.

Границы партии перечисляйте явно — поколения и варианты внутри поколения. Формулировка вида «все Galaxy S начиная с S9» понимается моделями по-разному: одна включит варианты FE и e, другая нет, и пересечение выгрузок для консенсуса окажется вдвое меньше возможного. Рабочий вид: «поколения S9, S10, S20, S21, S22, S23, S24, S25 — включая все варианты каждого поколения: базовый, Plus, Ultra, FE, e».

```
Ты составляешь технический справочник устройств для сервиса проверки поддержки eSIM.

ЗАДАЧА
Выдай данные по устройствам: ПАРТИЯ

ФОРМАТ ОТВЕТА
Только CSV, без пояснений до и после, без обёртки в блок кода.
Кодировка UTF-8, разделитель — запятая, значения с запятыми — в двойных кавычках.
Первая строка — ровно такой заголовок:
brand,marketing_name,model_codes,platform,device_type,release_year,esim_support,esim_conditions,dual_sim,max_esim_profiles,os_min_version,os_max_version,ru_market,source_url,confidence,notes

ДОПУСТИМЫЕ ЗНАЧЕНИЯ
platform: ios | android | harmonyos | other
device_type: phone | tablet | watch | laptop | other
esim_support: yes | no | conditional | unknown
dual_sim: physical+esim | dual-esim | esim-only | none | unknown
ru_market: official | parallel | none | unknown
confidence: high | medium | low

КРИТИЧЕСКИ ВАЖНЫЕ ПРАВИЛА
1. Не угадывай. Если не знаешь точно — пиши unknown в esim_support и оставляй поле пустым в остальных столбцах.
2. НЕ ВЫДУМЫВАЙ сервисные коды моделей (model_codes). Указывай только те, в которых уверен. Сомневаешься — оставь пустым. Пустое поле лучше неверного кода.
3. НЕ ВЫДУМЫВАЙ ссылки (source_url). Указывай только реально существующие страницы. Сомневаешься — оставь пустым.
4. Если поддержка eSIM зависит от региона продажи или версии устройства — ставь conditional и описывай условие в esim_conditions, например region:CN=no.
5. В confidence честно оценивай свою уверенность именно в значении esim_support.
6. Не сокращай перечень многоточием и не пиши «и другие». Если строк слишком много — выдай столько, сколько уместится, и в последней строке в поле notes укажи, на чём остановился.
7. marketing_name — официальное название без бренда, без объёма памяти и цвета.
8. Одна модель — одна строка. Региональные версии с разной поддержкой eSIM указывай через conditional, а не отдельными строками.
9. Не используй веб-поиск. Отвечай только тем, что знаешь сам, а неизвестное помечай unknown.
10. Строка нужна для каждой модели из задачи, даже если статус eSIM неизвестен: пропущенная строка и строка со значением unknown обрабатываются по-разному.
11. Не добавляй, не удаляй и не переставляй столбцы. В каждой строке ровно 16 полей.
12. Пустое поле — пустое. Не пиши N/A, -, null, «нет данных», 0 вместо пропуска.
13. Значения перечислимых полей — латиницей в нижнем регистре, ровно как в списке допустимых значений.
14. Не выравнивай столбцы пробелами и не добавляй пробелы после разделителя.
15. notes — одна строка не длиннее 200 символов, без переводов строк.
16. Строку заголовка выводи обязательно, первой, до любых данных.
17. В каждой строке ровно 15 запятых-разделителей. Пустое поле обозначается двумя запятыми подряд — не пропускай пустые поля, иначе значения сдвинутся в соседние столбцы. Перед выводом каждой строки пересчитай разделители.
18. model_codes: только полный код целиком, латиница, цифры и дефис. Не подставляй ?, *, X, квадратные скобки или иные знаки вместо неизвестной части кода. Не знаешь код целиком — оставь поле пустым.
19. os_min_version и os_max_version: только номер версии Android, например 9.0 или 14. Без слов Android, iOS, One UI и без версии оболочки производителя. В os_max_version указывай фактически вышедшую последнюю версию, а не расчёт по обещанному числу обновлений: обещание семи обновлений не повод писать версию, которой ещё нет.
20. esim_conditions: только пары ключ:значение через точку с запятой, например region:CN=no;region:US=esim-only. Это одно поле CSV, а не несколько: точка с запятой разделяет пары внутри поля и никогда не заменяет запятую между столбцами. Никакого свободного текста и оценочных слов (likely, some, varies, probably).
```

Правила 16–20 добавлены по итогам пилотного прогона (§А.8): каждое закрывает дефект, реально встреченный в выгрузках. Правило 17 — самое важное из них: пропущенное пустое поле сдвигает все последующие значения в соседние столбцы, и такая строка уходит в карантин целиком.

## А.5. Текст запроса для `families.csv`

Запрос сохранён как резерв и по ADR-021 в работу не идёт. Причина не в качестве формулировки: правило уровня линейки самостоятельно ничего не отвечает (§14.4, шаг 7 — статус `not_supported` появляется только после подтверждения модератором), а длинный хвост, ради которого запрос писался, уже перечислен поштучно в собранных партиях. Там, где есть запись о конкретном устройстве, правило линейки не нужно.

```
Ты составляешь справочник правил уровня товарных линеек для сервиса проверки поддержки eSIM.

ЗАДАЧА
Для каждой линейки смартфонов перечисленных брендов укажи, характерна ли для неё поддержка eSIM: ПАРТИЯ

ФОРМАТ ОТВЕТА
Только CSV, без пояснений, без обёртки в блок кода. Первая строка — ровно такой заголовок:
brand,family,years_from,years_to,esim_default,exceptions,confidence,notes

ДОПУСТИМЫЕ ЗНАЧЕНИЯ
esim_default: yes | no | mixed | unknown
confidence: high | medium | low

ПРАВИЛА
1. Не угадывай: не уверен — пиши unknown.
2. Если внутри линейки статус различается по моделям — ставь mixed и перечисли известные исключения в exceptions через символ |.
3. Указывай линейки, представленные на рынке России, начиная с 2018 года.
4. Не сокращай перечень многоточием.
```

К этому запросу применяются те же правила 9–20 из А.4 с поправкой на число столбцов: заголовок обязателен, в каждой строке ровно 8 полей и 7 запятых-разделителей.

Файлы: `03-samsung-fold-flip-note.csv`, `05-xiaomi-flagship.csv`, `08-huawei.csv`, `12-other-brands.csv` — по одному на каждый из пяти источников (кроме `gigachat-3-5-ultra`).

**Пригодность `qwen-3-7` на полной 16-столбцовой схеме подтверждена этим прогоном** (§А.1, правило 6): 0 строк `FIELD_COUNT_MISMATCH` из всех его строк по четырём партиям — то же свойство короткой схемы устойчивости к формату, что и на партии 16 (§А.10.4), теперь показано и на полной схеме `devices.csv`. Источник учтён в консенсусе на общих основаниях.

**Полный прогон партий 03/05/08/12 (все источники, 3034 строки во всём массиве вместе со старыми партиями).** Из строк новых партий: `SOURCE_DISAGREEMENT_UNRESOLVED` — 67 (весь объём этого кода на всём массиве приходится на новые партии — прямое противоречие `yes`/`no` без `conditional`, например Fairphone 4/5: три источника из четырёх утверждают `yes`, `gpt-5-6-luna` — `no` при внутренне противоречивой строке, `dual_sim: dual-esim` при `esim_support: no`); `ENUM_INVALID` — 149 (в основном `platform=""` у `deepseek-3-1/08-huawei` — источник не рискнул угадать `android`/`harmonyos` по правилу «не угадывай», но схема не допускает пустого значения); `YEAR_IMPLAUSIBLE` — 66 (тот же источник, та же партия — `release_year` пусто у всех строк Huawei); `CODE_COLLISION` — 29; `REFERENCE_MISMATCH` — 27 (пересечение с уже готовыми записями эталона по линейкам Z Fold/Z Flip/Note — см. §А.6 примечание и docs/08 §8.4); `DUPLICATE_MODEL_CODE` — 3; `NAME_COLLISION_CONFLICT` — 4; `CONFLICTING_ALIAS` — 3 (остаточный, тот же класс дефекта «двойной префикс», что у POCO/Redmi, ADR-029). `FIELD_COUNT_MISMATCH` и `CONDITION_SYNTAX_INVALID` — 0 у новых партий: формат выдержан всеми пятью источниками без исключения.

**Три дефекта пайплайна найдены и исправлены этим этапом** (docs/09 ADR-033): (1) бренды `Fairphone`, `HMD`, `Nokia` отсутствовали в словаре известных брендов (`tools/seed/src/domain/brands.ts`) — все их строки уходили в `BRAND_UNKNOWN` (170 строк); заодно исправлен обнаруженный при разборе карантина пробел партии 11а (`iQOO`, 89 строк, не входит в объём этого этапа, но того же класса). (2) Официальное название флагманов Xiaomi с 2022 года — чистое число без единого слова («12», «13 Pro» — по правилу §А.2 «без бренда»); прежняя проверка `NAME_UNPARSEABLE` считала отсутствие словесного токена признаком мусора и карантинила 273 такие строки. (3) Голое числовое `marketingName` тех же строк ложно конфликтовало как псевдоним между разными брендами (`CONFLICTING_ALIAS`, до 49 строк, включая 5 курируемых записей Apple) — псевдонимом это название быть не должно, потому что не несёт информации сверх самого бренда. Подробности и код всех трёх исправлений — ADR-033.

Партии 13 и 14 нужны не для полноты, а для корректного распознавания типа устройства: важно не выдать ответ про телефон пользователю планшета.

Состояние «курируемое ядро» у партий 1 и 9 требует пояснения, потому что его легко прочитать как «сделано» ещё до того, как данные заведены. У языковых моделей эти партии не запрашиваются по §А.1: перечни короткие, правила детерминированные, проверка вручную занимает минуты. Но отсутствие запроса к модели наличия данных не означает: пока `data/catalog/curated/` пуст, справочник по этой партии пуст тоже.

Партия 1 закрыта этапом 5.3: `data/catalog/curated/apple-iphone.json` содержит 44 записи (от iPhone 6 до iPhone 17 Pro Max, iPhone Air и 17e, включая SE всех трёх поколений) с сигнатурами экранов, диапазонами версий iOS и ссылками на вендорские страницы Apple. Оценка «~35 строк» относилась к перечню на момент составления приложения и с тех пор выросла на поколения 16/17, Air и модели `e`. Партия 9 (Google Pixel) закрыта этапом 5.4 (ADR-032): `data/catalog/curated/google-pixel.json` содержит 32 записи от Pixel (2016) до Pixel 10 Pro Fold со ссылками на support.google.com/pixelphone.

## А.7. Что делать с полученными файлами

1. Сохранить как есть, без ручной правки, в `data/catalog/import/<источник>/<партия>.csv`. Ручные правки до импорта нежелательны: они смешивают проверенные и непроверенные данные и делают отчёт об импорте недостоверным. Слаг источника содержит версию модели: `gpt-5-6-luna`, а не `gpt` — через полгода источник без версии перестаёт что-либо означать.
2. Положить рядом `source.txt` с метаданными: точное название и версия модели, дата запроса, режим веб-поиска, номер и границы партии, использованная формулировка. Эти значения попадают в поле `provenance` каждой записи справочника.
3. Запустить импорт в режиме проверки: `pnpm seed import --source <слаг-источника> --dry-run` (путь к файлу не передаётся аргументом — конвейер сам находит `data/catalog/import/<источник>/*.csv`, docs/14 §14.5; значение `--source` — это ИМЯ ПАПКИ источника, например `gpt-5-6-luna`, без префикса `llm:` — обнаружено этапом 5.5 при попытке использовать буквальный пример из документа, `--source llm:<модель>`, который не совпадает ни с одной реальной папкой).
4. Изучить отчёт: доля карантина по кодам нарушений и расхождения с эталоном.
5. При наличии выгрузок от нескольких моделей выполнить `pnpm seed consensus`.
6. Загрузить принятые записи и разобрать очередь модерации, начиная с самых частых обращений.

Ожидаемая доля карантина при первой выгрузке — от 10 до 25% строк. Это нормальный результат: карантин означает, что проверки сработали, а не что выгрузка неудачна.

Про повторные прогоны действуют два правила. Первое: дополнять формулировку между прогонами допустимо только правилами формата — они не меняют того, что модель думает о поддержке eSIM, поэтому сравнимость с остальными источниками сохраняется. Правка содержательных правил требует перезапуска всех источников, иначе консенсус сравнивает ответы на разные вопросы. Второе: **два прогона одной модели — один источник консенсуса**, независимо от того, насколько разошлись их ответы. Неудачный прогон не удаляется: файл с дефектами формата ценен как фикстура парсера.

## А.8. Результаты выгрузок

### А.8.1. Пилотная партия

Партия 02 (Samsung Galaxy S, поколения S9–S25) запрошена у четырёх моделей с выключенным веб-поиском. Пилот проверял пригодность источников и формулировку до массового прогона остальных партий.

| Источник                   | Заголовок | Строк данных | Строк с верным числом полей | Пригоден |
| -------------------------- | --------- | ------------ | --------------------------- | -------- |
| `gpt-5-6-luna`             | есть      | 28           | 26                          | да       |
| `deepseek-3-1`             | есть      | 27           | 27                          | да       |
| `gemini-3-6-flash`         | есть      | 32           | 32                          | да       |
| `gigachat-3-5-ultra` run 1 | нет       | 24           | 2                           | нет      |
| `gigachat-3-5-ultra` run 2 | есть      | 26           | 0                           | нет      |

Итог консенсуса по трём пригодным источникам: 29 устройств, из них 25 на уровне `derived` и 4 на уровне `unverified`. Расхождения источников — 4 записи, все разрешены правилом осторожности, прямых противоречий `yes`/`no` нет ни одного.

Выводы, применимые к остальным партиям:

1. **Разъехавшиеся столбцы — основной класс дефекта, а не обрыв перечня.** Обрывов не было ни у одной модели; пропущенные пустые поля были у двух моделей из четырёх. Отсюда правило 17 и код проверки `FIELD_COUNT_MISMATCH`. Цена дефекта наглядна: две сломанные строки `gpt-5-6-luna` пришлись на Galaxy S9 и S9+, и обе записи из-за этого остались без второго подтверждающего источника.
2. **Отбраковка источника целиком — нормальный исход.** GigaChat 3.5 Ultra исключён: второй прогон с более строгой формулировкой дал результат хуже первого (правило про пары `ключ:значение` понято как разрешение схлопнуть половину схемы в одно поле через `;`), плюс `confidence: high` во всех строках без единого `unknown` и один сервисный код, присвоенный двум разным устройствам. Источник, который никогда не воздерживается, для консенсуса бесполезен. Оба файла оставлены как фикстуры.
3. **Согласие источников достигается в основном на значении `conditional`.** Из 29 устройств 24 получили статус `conditional`. То есть справочник, собранный только из выгрузки, задавал бы уточняющий вопрос почти на каждом устройстве Samsung. Однозначный ответ здесь даёт не выгрузка, а суффикс сервисного кода: он кодирует регион (`B` — Европа, `0` — Китай, `U` — США), а регион определяет наличие eSIM. Полного набора суффиксов не дала ни одна модель, все ограничились европейским вариантом — это работа курируемого ядра, см. [11-implementation-plan.md](./11-implementation-plan.md), этап 1, дорожка Б.
4. **Расхождения источников кучкуются на границе появления технологии.** Все четыре расхождения пришлись на Galaxy S10, S10+, S10e и S20 FE — то есть на рубеж, где eSIM в линейке Samsung появилась. Один источник считает эти устройства не поддерживающими eSIM, другой — поддерживающими условно. Это готовый и приоритетный список моделей для `catalog.reference.json`: подтверждение границы вручную снимает сразу целую группу расхождений. **Разрешено этапом 5.4 (ADR-032):** по официальной вендорской странице Samsung (`samsung.com/.../galaxy-esim-and-supported-network-carriers/`, «Galaxy devices that support eSIM») ни Galaxy S10/S10+/S10e, ни Galaxy S20 FE в перечень поддерживающих eSIM устройств не входят — все четыре получили в эталоне статус `no` (S10+ неотличим от S10 общим для конвейера свойством нормализации, docs/09 ADR-032 п.5, а не отдельной записью).
5. **Разное написание одной модели между источниками проблемой не является.** Одна модель перечисляет устройства как `Galaxy S21`, другая — как `Galaxy S21 5G`. Признак сети `5G` — незначимый атрибут, в детерминированный идентификатор он не входит, поэтому записи сходятся; подробно — [14-catalog-ingestion.md](./14-catalog-ingestion.md), шаг 2. Запрашивать у моделей единообразие названий не нужно.

Выводы, дополняющие пилотные:

6. **Отбраковка источника по частоте воздержаний была бы ошибкой, и пилот к ней подталкивал.** Основанием исключить `gigachat-3-5-ultra` служило несоблюдение схемы CSV, и только оно. Полный прогон показал, что по доле `unknown` худший источник — не он, а `gemini-3-6-flash` с нулём воздержаний и `confidence: high` в 99% строк. Признак «модель никогда не воздерживается» — повод для недоверия к её уверенности, а не критерий пригодности источника.
7. **Заполненность сервисных кодов обратно связана с их достоверностью.** `gemini-3-6-flash` заполнил коды в 98% строк против 14–20% у остальных, и на этом же источнике сосредоточены все существенные дефекты: 29 нарушений вендорских шаблонов и 10 коллизий, где один код присвоен двум разным устройствам (`SM-A217F` для Galaxy A21 и A21s, `RMX3888` для realme 9 5G и GT5 Pro, `V2309A` для iQOO 12 Pro и X100). `gpt-5-6-luna`, заполнивший коды в 14% строк, не дал ни одного нарушения шаблона и ни одной коллизии. Это подтверждает предметное правило 4 в `AGENTS.md` и означает, что при слиянии приоритет по полю `model_codes` определяется не полнотой источника, а прохождением валидации.
8. **Половина массива покрыта единственным источником.** 497 устройств из 999 имеют статус только от одной модели и потому остаются на уровне `unverified`, то есть в ответах пользователю не участвуют. Причина не в браке выгрузок, а в разном понимании границ партии: длинный хвост брендов каждая модель перечисляет по-своему. Увеличивать число источников ради этих записей нерационально — дешевле сузить границы партий, как это сделано для партий 04, 06, 10 и 11, либо закрывать пробелы модерацией по частоте обращений.

## А.10. Партия 16: суффиксы сервисных кодов и регион продажи

Это самая дешёвая по объёму запроса и самая дорогая по влиянию на охват партия. Из 29 устройств пилота 24 получили статус `conditional` из-за условия `region:CN=no` (§А.8.1, вывод 3), то есть справочник, собранный только из выгрузки, задавал бы уточняющий вопрос почти на каждом Samsung. При этом регион уже приходит в сигнале: суффикс кода `SM-S928B` из заголовка `Sec-CH-UA-Model` кодирует Европу, и там, где суффикс известен, уточняющий вопрос не нужен. Само множество суффиксов маленькое и замкнутое — порядка полутора десятков значений на вендора.

### Схема `code-suffixes.csv`

Шесть столбцов, пять запятых-разделителей. Кодировка UTF-8, разделитель — запятая.

Столбца, описывающего влияние суффикса на наличие eSIM, схема не содержит (ADR-028, docs/09-decisions.md): таблица суффиксов отвечает только на вопрос «какому региону соответствует код», а не «поддерживает ли устройство eSIM» — второе остаётся исключительно на уровне записи устройства (`devices.esim`, docs/05-data-model.md §5.4). Прогон партии 16 показал, что столбец, отвечавший на оба вопроса разом, породил кажущееся противоречие источников там, где они были согласны — разбор в §А.10.4.

| Столбец        | Обязателен | Допустимые значения                                                                              | Пояснение                                            |
| -------------- | ---------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| `brand`        | да         | Латиницей, как в `devices.csv`                                                                   | Бренд, к схеме кодов которого относится суффикс      |
| `code_suffix`  | да         | Суффикс ровно как в коде, с сохранением регистра: `B`, `U1`, `0`, `AL00`                         | Часть кода после номера модели; регистр значим       |
| `code_example` | нет        | Полный реально существующий код, оканчивающийся этим суффиксом                                   | **Только при уверенности.** Пусто, если не уверены   |
| `region`       | да         | `eu`, `ru`, `ca`, `cn`, `us`, `kr`, `in`, `jp`, `tr`, `latam`, `mea`, `sea`, `global`, `unknown` | Регион или рынок продажи устройств с таким суффиксом |
| `confidence`   | да         | `high`, `medium`, `low`                                                                          | Уверенность именно в связке «суффикс → регион»       |
| `notes`        | нет        | Свободный текст, одна строка до 200 символов                                                     | Существенные оговорки                                |

### Текст запроса

```
Ты составляешь справочник соответствий «суффикс сервисного кода модели → регион продажи» для сервиса проверки поддержки eSIM.

ЗАЧЕМ ЭТО НУЖНО
Браузер сообщает нам сервисный код устройства целиком, например SM-S928B. У ряда брендов последние символы кода указывают на регион, для которого выпущено устройство. Нам нужно множество таких суффиксов и регионов, которым они соответствуют — не более того: влияние региона на наличие eSIM у конкретного устройства мы определяем сами по данным об этом устройстве, а не по этой таблице.

ЗАДАЧА
Перечисли известные тебе суффиксы сервисных кодов и регионы, которым они соответствуют, для брендов:
- Samsung, коды вида SM-XXXXX — все буквенные и цифровые окончания, которые встречаются у смартфонов, выпущенных с 2019 года;
- Huawei и Honor, коды вида ABC-XXNN;
- Xiaomi, OPPO, OnePlus, realme, vivo, ZTE — только если у бренда есть регулярная схема региональных окончаний кода. Если схемы нет и региональные версии различаются целиком другим кодом, дай для этого бренда ровно одну строку в таком виде: code_suffix=unknown, code_example пусто, region=unknown, confidence=low, причина в notes. Обязательные поля в этой строке не оставляй пустыми.

ФОРМАТ ОТВЕТА
Только CSV, без пояснений до и после, без обёртки в блок кода.
Кодировка UTF-8, разделитель — запятая, значения с запятыми — в двойных кавычках.
Первая строка — ровно такой заголовок:
brand,code_suffix,code_example,region,confidence,notes

ДОПУСТИМЫЕ ЗНАЧЕНИЯ
region: eu | ru | ca | cn | us | kr | in | jp | tr | latam | mea | sea | global | unknown
confidence: high | medium | low

КРИТИЧЕСКИ ВАЖНЫЕ ПРАВИЛА
1. Не угадывай. Не знаешь регион для суффикса — пиши unknown в region и low в confidence, но саму строку оставляй.
2. НЕ ВЫДУМЫВАЙ суффиксы. Перечисляй только те, которые действительно встречал в кодах реальных устройств. Полный короткий список лучше длинного с догадками.
3. НЕ ВЫДУМЫВАЙ примеры кодов (code_example). Указывай только реально существующий код целиком. Сомневаешься — оставь поле пустым.
4. code_suffix — ровно те символы, которыми оканчивается код, с сохранением регистра. Не подставляй ?, *, X, квадратные скобки или иные знаки вместо неизвестной части.
5. Одна строка — один суффикс одного бренда. Не объединяй несколько суффиксов в одной строке.
6. Если один и тот же суффикс у бренда означает разные регионы, дай отдельную строку на каждый регион и поясни различие в notes.
7. Не сокращай перечень многоточием и не пиши «и другие».
8. Не используй веб-поиск. Отвечай только тем, что знаешь сам, а неизвестное помечай unknown.
9. Строку заголовка выводи обязательно, первой, до любых данных.
10. В каждой строке ровно 6 полей и ровно 5 запятых-разделителей. Пустое поле обозначается двумя запятыми подряд. Перед выводом каждой строки пересчитай разделители.
11. Пустое поле — пустое. Не пиши N/A, -, null, «нет данных».
12. Значения region и confidence — латиницей в нижнем регистре, ровно как в списке допустимых значений. Регистр code_suffix и code_example не меняй.
13. Не выравнивай столбцы пробелами и не добавляй пробелы после разделителя.
14. notes — одна строка не длиннее 200 символов, без переводов строк.
```

Схема и текст запроса выше не содержат влияния суффикса на наличие eSIM ни в одном виде (столбец, допустимое значение, правило) — правка внесена по ADR-028: столбец `esim_effect` прежней схемы сжимал в одно значение два разных факта («суффикс меняет статус» и «у устройства нет eSIM вовсе»), что и породило кажущееся противоречие §А.10.4 по Huawei. Если партия будет запрошена у новой модели заново, вопрос звучит только про регион.

### Что делать с результатом

1. Файл сохранить как `data/catalog/import/<слаг-источника>/16-code-suffixes.csv`, дописав блок в `source.txt` этой папки по образцу остальных партий. Для нового источника слаг содержит версию модели (`qwen-3-5-max`, а не `qwen`) — §А.7, пункт 1.
2. Запрос короткий, поэтому его стоит отправить всем доступным источникам, а не одному — но не ради правила консенсуса §14.5 (эта партия не его вход, см. пункт 3), а ради более широкого перечня кандидатных связок «суффикс → регион» на входе следующего пункта: разные источники называют разные подмножества суффиксов (§А.10.4 — из 63 связок только 25 названы двумя и более источниками), и объединение этих перечней — источник кандидатов, а не голосов.
3. **Выгрузка сама по себе не отменяет уточняющий вопрос и не является входом правила консенсуса (ADR-013, ADR-026, ADR-028).** Чтобы суффикс превращал `conditional` в однозначный ответ, связка «суффикс → регион» должна иметь уровень `verified`, а его даёт исключительно ручная сверка с вендорскими источниками — реальная ссылка и дата проверки (`sources[].url`, `checkedAt`), а не совпадение нескольких выгрузок между собой. Согласие источников из §А.10.4 (например, шесть связок с тремя и более источниками) ускоряет ручную сверку тем, что подсказывает, с чего начинать, но само по себе `verified` не даёт. Проверенное множество ведётся как данные в `data/catalog/code-suffixes.json` рядом с `code-patterns.json`, по схеме без столбца влияния на eSIM (ADR-028), и является частью курируемого ядра (ADR-026).
4. Порядок именно такой, а не обратный: выгрузка нужна для того, чтобы ручная сверка начиналась с готового перечня кандидатов, а не с пустого листа. Проверить полтора десятка значений по вендорским страницам быстро; вспомнить, какие значения вообще существуют, — медленно.

### А.10.4. Результат прогона

Партия запрошена у пяти источников: к четырём источникам `devices.csv` добавлен `qwen-3-7`. Схема из семи столбцов выдержана лучше шестнадцати: **неверного числа полей нет ни в одной строке из 125** — это прямое подтверждение того, что короткая строка устойчивее к основному классу дефекта из §А.8.2.

| Источник             | Строк | Полей верно | Пустые обязательные поля | Доля `high` | Замечания                                                     |
| -------------------- | ----- | ----------- | ------------------------ | ----------- | ------------------------------------------------------------- |
| `gemini-3-6-flash`   | 35    | 35          | 0                        | 83%         | Ни одного воздержания; суффиксы `B/DS`, `E/DS`, `JPN`, `00`   |
| `qwen-3-7`           | 30    | 30          | 0                        | 80%         | Ни одного `medium`; один код-пример на два бренда (`BVL-NX9`) |
| `gpt-5-6-luna`       | 26    | 26          | 6                        | 54%         | Честно отметил, что Канада в наборе `region` отсутствует      |
| `deepseek-3-1`       | 20    | 20          | 0                        | 35%         | Самый осторожный; воздержался по суффиксу `B` целиком         |
| `gigachat-3-5-ultra` | 14    | 14          | 6                        | 36%         | Код целиком вместо суффикса; буква `O` вместо цифры `0`       |

Всего 63 связки «бренд + суффикс», из них 25 названы двумя и более источниками.

**Что подтверждено согласием и годится в работу первым.** Шесть связок имеют три и более источника без расхождений: `SM-*0` → Китай, eSIM отсутствует (4 источника); `SM-*U` → США (5) и `SM-*U1` → США (4); `*-AL00` у Huawei → Китай, eSIM отсутствует (4); `*-AN00` → Китай, eSIM отсутствует (по 3 источника у Huawei и у Honor). Это и есть практически значимая часть: условие `region:CN=no`, из-за которого 24 из 29 устройств пилота получили `conditional` (§А.8.1, вывод 3), закрывается двумя суффиксами — `0` у Samsung и `AL00`/`AN00` у Huawei и Honor.

**Где источники противоречат друг другу прямо.** Расхождения не рассыпаны по таблице, а собраны в двух местах, и оба поучительны.

1. **Влияние суффикса на eSIM у Huawei.** `qwen-3-7` считает, что eSIM нет ни у одной версии Huawei, включая европейские `L09`, `L21`, `L29`; `gemini-3-6-flash` и `deepseek-3-1` считают, что у них eSIM есть. Это прямое противоречие `supported` против `not_supported` без единого `conditional`, то есть по §14.5 карантин и разбор человеком, а не автоматическое разрешение.
2. **Регион суффикса `W` у Samsung.** Три источника называют Канаду (`gpt-5-6-luna` при этом честно пишет, что Канады нет в наборе значений), а `gigachat-3-5-ultra` относит `W` к Китаю — и это не безобидная ошибка в справочной строке, а готовый ложный отрицательный ответ: регион `cn` тянет за собой `not_supported`. Тот же источник отнёс `N` к Европе против трёх источников, назвавших Корею.

**Вывод: противоречие по Huawei — артефакт схемы опроса, а не расхождение источников по существу (ADR-028).** Перечитав ответы всех пяти источников не по столбцу `esim_effect`, а по существу, расхождения по Huawei нет: все пять согласны, что европейский суффикс `L09`/`L21`/`L29` регионально ничем не отличается от прочих версий, и отдельно все пять согласны, что у этой линейки Huawei eSIM нет вовсе, независимо от региона. `qwen-3-7` ответил на вопрос «есть ли eSIM у устройства», `gemini-3-6-flash` и `deepseek-3-1` — на вопрос «отличается ли региональная версия», а столбец `esim_effect` требовал одного значения на оба вопроса и тем самым сталкивал их лбами там, где столкновения не было. Ровно поэтому ADR-028 убирает этот столбец из схемы: таблица суффиксов задаёт только связку «суффикс → регион», а вопрос про eSIM самого устройства остаётся на уровне записи `devices.esim` (docs/05 §5.4), где для него и так есть детерминированные условия (docs/05 §5.4, случай для Huawei разбирается отдельно записью устройства, а не таблицей суффиксов).

**Три дефекта формулировки, обнаруженные прогоном, и правки, внесённые по их итогам.**

- В наборе `region` не было Канады, хотя `W` — распространённый суффикс. Один источник написал `unknown` с пояснением, два выдали `global`, то есть потеряли сведение. Добавлено значение `ca`.
- Строка «у бренда нет регулярной схемы» была задана недостаточно строго: сказано только про `code_suffix=unknown`. В результате три источника закодировали её тремя разными способами — пустой `region`, `unknown` во всех полях, `unknown` в `confidence` (значение вне набора). Отсюда все 12 строк с пустыми обязательными полями у `gpt-5-6-luna` и `gigachat-3-5-ultra`. Требуемый вид строки теперь перечислен поля-в-поле.
- `same_as_global` и `supported` — ответы на разные вопросы, и при слиянии их нельзя считать расхождением: первый говорит «суффикс ничего не меняет», второй — «eSIM есть». У `SM-*U` источники дали оба значения, и это согласие, а не конфликт. Правило слияния: `same_as_global` не даёт статуса eSIM сам по себе, он лишь запрещает выводить из суффикса отрицательный ответ.

**Отдельная зацепка для ручной проверки.** Четыре источника утверждают, что у Xiaomi регулярной схемы региональных суффиксов нет, а `deepseek-3-1` называет схему `G` — глобальная версия, `C` — Китай, `I` — Индия с примерами вида `M2001J2G`. Меньшинство здесь выглядит правдоподобнее большинства, и проверка одного этого утверждения потенциально закрывает регион для всей линейки Redmi и POCO — самой массовой части собранного массива.

**Режим веб-поиска (вопрос снят).** Партии 02 и 04а–11б запрашивались с выключенным поиском (§А.1, правило 5). Для партии 16 режим не был зафиксирован при запросе: он отправлялся с настройками интерфейса по умолчанию, где поиск, как правило, включён, при том что правило 8 формулировки (было правилом 9 до исключения `esim_effect`) требует поиском не пользоваться. Раньше это оставалось открытым вопросом именно потому, что партия 16 по построению рассматривалась как ещё один вход правила консенсуса (§14.5), а для консенсуса независимость источников — необходимое условие, и незафиксированный поиск эту независимость мог нарушить незаметно.

Вопрос снимается не задним числом ослабленным требованием, а явным определением роли партии 16, зафиксированным в §А.10 пункте 3 и ADR-026/ADR-028: **эта партия не вход правила консенсуса, а генератор перечня кандидатов для последующей ручной сверки с вендорскими страницами.** Ни одна связка «суффикс → регион» не получает статус `verified` по факту согласия источников — его даёт только ссылка на вендорский источник и дата сверки (ADR-026), то есть тот же критерий, который бы применялся и без выгрузки вовсе. Независимость источников партии 16 не участвует в решении о `verified` и потому неважно, был ли у части из них включён поиск. Данные это не обесценивает, и перезапрашивать партию не нужно. Если партия когда-нибудь будет запрошена заново, режим стоит тем не менее выбрать сознательно и одинаковым для всех источников — при включённом поиске правило про запрет поиска заменяется на требование указывать ссылку, а схема получает дополнительный столбец `source_url` — иначе ссылки, ради которых поиск включался, останутся в переписке модели, а не в CSV.

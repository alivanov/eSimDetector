# 7. Интеграция, развёртывание и настройка

## 7.1. Три уровня интеграции

Заказчик выбирает уровень в зависимости от того, насколько плотно решение должно врастать в его продукт.

| Уровень      | Что подключается                     | Трудозатраты                      | Кому подходит                                                     |
| ------------ | ------------------------------------ | --------------------------------- | ----------------------------------------------------------------- |
| 1. Виджет    | Один тег `<script>` и один контейнер | Минуты                            | Лендинги, статические страницы, CMS                               |
| 2. Компонент | Пакет npm с React-компонентом        | Часы                              | Личный кабинет, мобильное веб-приложение                          |
| 3. API       | Прямые вызовы REST                   | По объёму собственного интерфейса | Собственный дизайн, мобильные приложения, чат-боты, контакт-центр |

Все три уровня работают на одном и том же API, поэтому логика определения и результаты идентичны независимо от способа подключения.

## 7.2. Уровень 1: виджет

```html
<div id="esim-checker"></div>
<script
  src="https://esim-detector.example.ru/widget/v1/esim-widget.js"
  data-target="#esim-checker"
  data-api-base="https://esim-detector.example.ru"
  data-theme="sbermobile"
  data-channel="landing-esim"
  defer
></script>
```

**`data-api-base` — адрес БЕЗ версионированного пути** (только протокол и хост, без `/api/v1`):
клиент виджета добавляет `/api/v1/...` к каждому запросу сам (`apps/widget/src/api/http.ts`,
docs/06-api-contract.md §6.1). Значение с уже дописанным `/api/v1` (как в более ранней редакции
этого примера) привело бы к продублированному пути запроса — исправлено этапом 6.3 (ADR-040), тот
же дефект актуален для примера `apiBase` в §7.3 ниже, но его правка — объём уровня 2 интеграции
(пакет npm, вне этапа интерфейса).

Свойства реализации:

- виджет собирается в один самодостаточный файл без внешних зависимостей рантайма (реализовано:
  `apps/widget/vite.config.mts`, режим библиотеки Vite, формат IIFE, путь `widget/v1/esim-widget.js`);
- рендерится как Web Component (`<esim-detector-widget>`, `apps/widget/src/web-component/`) с
  теневым DOM — стили страницы заказчика и стили виджета взаимно изолированы. Сам этот тег не
  пишется заказчиком в разметке — скрипт подключения создаёт его и вставляет в контейнер
  `data-target` программно, поэтому разметка подключения ограничивается примером выше;
- сигналы устройства собираются автоматически; автоопределение запускается сразу при появлении
  виджета в области видимости через `IntersectionObserver` (окружения без него — устаревшие
  браузеры — монтируют виджет немедленно, деградация без отказа);
- события жизненного цикла публикуются наружу, что позволяет заказчику встроить виджет в собственную аналитику и продолжить сценарий подключения eSIM:

```js
document.querySelector('#esim-checker').addEventListener('esim:result', (e) => {
  // e.detail = { status, deviceId, confidence, exactModelKnown }
});
```

Полный перечень событий: `esim:ready`, `esim:detected`, `esim:clarification`, `esim:result`, `esim:error`, `esim:action` (нажатие основного действия — точка перехода в сценарий подключения). Все шесть — `CustomEvent` на элементе `<esim-detector-widget>` (вложен в контейнер `data-target`, поэтому обработчик, навешанный на сам контейнер, как в примере выше, получает событие всплытием) с `bubbles: true` и `composed: true` — без `composed` событие не пересекло бы границу теневого DOM. Форма `esim:result` зафиксирована выше буквально; формы остальных пяти определены этапом 6.3 и зафиксированы ADR-040 (docs/09-decisions.md):

| Событие              | Когда публикуется                                                                                                                                                                 | `detail`                                                                                                  |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `esim:ready`         | Пользовательский элемент подключён к документу и инициализирован (теневой DOM создан, стили токенов вставлены) — до появления в области видимости и до первого запроса            | `{ channel: string \| null }`                                                                             |
| `esim:detected`      | Получен и разобран ответ `/detect` (автоопределение по сигналам браузера) — независимо от того, требуется ли после этого уточнение; НЕ публикуется для результатов ручного поиска | `{ method: string, platform: Platform, deviceType: DeviceType, exactModelKnown: boolean }`                |
| `esim:clarification` | Ответ (от `/detect` либо от ручного поиска) содержит блок `clarification` — дополнительно к `esim:result`, поскольку форма последнего фиксирована и не включает деталей уточнения | `{ kind: ClarificationKind, question: string, options: Array<{ id: string, label: string }> }`            |
| `esim:result`        | Показан один из трёх статусов результата                                                                                                                                          | `{ status, deviceId: string \| null, confidence: number, exactModelKnown: boolean }`                      |
| `esim:error`         | Показан экран ошибки взаимодействия (сеть недоступна либо ответ сервиса кодом 4xx/5xx)                                                                                            | `{ code: string, message: string }`                                                                       |
| `esim:action`        | Клик по действию с `kind: 'continue'` («Подключить eSIM») — точка перехода в сценарий подключения заказчика                                                                       | `{ kind: 'continue', label: string, deviceId: string \| null, status: ResultStatus, confidence: number }` |

`Platform`/`DeviceType`/`ResultStatus`/`ClarificationKind` — те же перечисляемые значения границы API, что в docs/06-api-contract.md §6.1/§6.2 (клиент виджета объявляет их копией у себя, `apps/widget/src/api/enums.ts`, `.../api/clarification.ts` — ADR-037/ADR-039). `code` события `esim:error` — `'NETWORK'` (сеть недоступна/CORS), `'PARSE_ERROR'` (ответ не разобран) либо код ошибки из реестра §6.5 (`CATALOG_UNAVAILABLE`, `RATE_LIMITED` и т. д.).

**Действие `kind: 'continue'` («Подключить eSIM») и обработчик.** API по-прежнему отдаёт `presentation.primaryAction` с `kind: 'continue'` в теле ответа (docs/06 §6.2) — тексты контракта для интегратора не меняются. Виджет и React-компонент **не рисуют** эту кнопку, пока интегратор не передал обработчик: у Web Component он есть всегда (публикуется `esim:action`), у `EsimChecker` — проп `onPrimaryAction`. Демонстрационная страница `/` обработчик намеренно не передаёт: сценария подключения eSIM на стенде нет, мёртвая кнопка не показывается. Ссылка «Указать устройство вручную» внизу виджета скрывается, если на экране уже есть переход к ручному вводу (`clarification.kind === 'manual_input'` или действие `manual_search`).

## 7.3. Уровень 2: компонент React

```tsx
import { EsimChecker } from '@sbermobile/esim-detector-react';

<EsimChecker
  apiBase="https://esim-detector.example.ru/api/v1"
  channel="lk-web"
  onResult={(r) => analytics.track('esim_check', r)}
  onPrimaryAction={(action) => {
    // переход в сценарий подключения eSIM заказчика
  }}
/>;
```

Без `onPrimaryAction` кнопка «Подключить eSIM» не отображается (§7.2 выше) — это ожидаемое поведение, а не дефект ответа API.

## 7.5. Client Hints: важное для интегратора

Модель Android-устройства доступна только через User-Agent Client Hints. Способ получения зависит от того, как встроено решение, и это единственное место, где интеграция требует внимания.

| Способ встраивания                                            | Как получается модель                                             | Что нужно от заказчика                                                                              |
| ------------------------------------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Виджет или React-компонент на странице заказчика              | JavaScript-вызов `navigator.userAgentData.getHighEntropyValues()` | **Ничего.** Вызов доступен любому скрипту в документе                                               |
| Собственный интерфейс заказчика, сигналы собираются его кодом | Тот же JavaScript-вызов                                           | Передать полученные значения в поле `signals.uaData`                                                |
| Определение по HTTP-заголовкам на стороне сервера заказчика   | Заголовки `Sec-CH-UA-Model`, `Sec-CH-UA-Platform-Version`         | Выставить `Accept-CH` и `Critical-CH` в ответе своего сервера                                       |
| Виджет во вложенном iframe с другого домена                   | Заголовки в iframe                                                | Делегировать подсказки: `Permissions-Policy: ch-ua-model=(self "https://esim-detector.example.ru")` |

Отсюда следует рекомендация по умолчанию: **встраивать виджет скриптом на страницу, а не через iframe.** В этом случае решение работает с максимальной точностью и не требует от заказчика вообще никаких настроек на его инфраструктуре, что и есть требование ТЗ о минимальных усилиях команды заказчика. Вариант с iframe поддерживается для случаев жёстких ограничений политики безопасности контента, но точность определения на Android в нём зависит от делегирования подсказок.

Наш собственный сервер выставляет `Accept-CH` и `Critical-CH` самостоятельно — для сценария, когда пользователь открывает демонстрационную страницу напрямую.

## 7.6. Развёртывание демонстрационного контура

Требования к окружению: Docker и Docker Compose. Иных зависимостей нет.

```bash
git clone <repository-url>
cd esim-detector
cp .env.example .env      # шаг не обязателен: значения по умолчанию рабочие
docker compose up -d

# Наполнение справочника — отдельный разовый шаг из двух команд (ADR-015), см. абзац ниже.
# MONGODB_URI обязателен: по умолчанию tools/seed обращается к хосту `mongo`, который
# резолвится внутри сети Docker, но не на машине разработчика.
pnpm install
MONGODB_URI=mongodb://localhost:27017/esim pnpm seed load
MONGODB_URI=mongodb://localhost:27017/esim pnpm seed rebuild-signatures
docker compose restart api   # API читает справочник и сигнатуры один раз при старте
```

После запуска доступны:

| Адрес                                            | Назначение                                                                |
| ------------------------------------------------ | ------------------------------------------------------------------------- |
| `http://localhost:8080`                          | Демонстрационное приложение (русский интерфейс)                           |
| `http://localhost:8080/debug`                    | Стенд отладки: разбор произвольных сигналов (см. абзац ниже)              |
| `http://localhost:8080/admin`                    | Модерация справочника (docs/15-moderation.md §15.7) — за `ADMIN_TOKEN`    |
| `http://localhost:8080/widget/v1/esim-widget.js` | Собранный файл виджета — тот же путь, что и в примере §7.2                |
| `http://localhost:8080/widget-example/`          | Пример подключения виджета одним тегом `<script>` на «странице заказчика» |
| `http://localhost:3000/api/docs`                 | Swagger UI с примерами                                                    |
| `http://localhost:3000/api/v1/catalog/meta`      | Версия и объём загруженного справочника                                   |
| `http://localhost:3000/health/ready`             | Готовность сервиса                                                        |

**Наполнение справочника — отдельный шаг из ДВУХ команд, а не часть `docker compose up` (уточнение агента 6.6, docs/09-decisions.md ADR-042).** Раздел прежде утверждал, что справочник наполняется автоматически при первом запуске — это противоречило уже принятому ADR-015 («загрузка выполняется отдельным разовым шагом до старта API... запрещена загрузка справочника при старте приложения») и фактическому `docker-compose.yml` (сервис `api` не содержит шага загрузки). После `docker compose up -d` справочник пуст (`GET /api/v1/catalog/meta` отвечает `deviceCount: 0`), пока не выполнен `pnpm seed load` с `MONGODB_URI`, указывающим на тот же кластер, что и у запущенного `api` (тот же приём, что и для публичного стенда на Render, §7.6а ниже). Правка исходного кода для демонстрации базового сценария не требуется — это прямое требование критерия К4; оба шага наполнения выполняются один раз перед первым обращением.

**Вторая команда, `pnpm seed rebuild-signatures`, обязательна и пропускается чаще всего.** Она строит производную коллекцию `screen_signatures` из уже загруженных `devices` (`tools/seed/src/commands/rebuild-signatures.ts` читает устройства ИЗ БАЗЫ, поэтому порядок `load` → `rebuild-signatures` жёсткий). Пропуск не проявляется ни одной ошибкой: `GET /health/ready` отвечает `ok`, потому что готовность считается по `devices` и `catalog_overrides` (`apps/api/src/modules/catalog/catalog.service.ts`), а ветка iOS не падает, а деградирует — теряет сужение по геометрии экрана (docs/03 §3.5, шаг 2) и работает только по правилу версии ОС. Практическое следствие: владелец iPhone получает широкий список кандидатов вместо узкой группы, то есть уточнение там, где возможен однозначный ответ. Ложного результата это не даёт (AGENTS.md, предметное правило 1), но заметно ухудшает демонстрацию на самом массовом сегменте устройств.

**Учёт `catalog_overrides` при пересборке (этап 7, docs/09-decisions.md ADR-043).** `pnpm seed rebuild-signatures` теперь читает и `devices`, и `catalog_overrides`, применяя решения модератора (`applyCatalogOverride`) ПЕРЕД пересборкой — без этого повторный `pnpm seed load && pnpm seed rebuild-signatures` после массового переимпорта стирал бы из `screen_signatures` привязки сигнатур, сделанные через раздел `/admin`, хотя сам слой `catalog_overrides` остаётся цел. Для ТОЧЕЧНОГО решения модератора («привязать сигнатуру», §15.4) эту пару команд выполнять не нужно вовсе — `CatalogWriteService` пересобирает затронутую запись `screen_signatures` сама, в рамках одного запроса `POST /api/v1/admin/moderation/tasks/{id}/resolve` (docs/15 §15.4, §15.8).

**Третий шаг — `docker compose restart api`, либо `POST /api/v1/admin/catalog/reload` (этап 7, docs/15-moderation.md §15.8; docs/09-decisions.md ADR-043).** Оба кэша читаются один раз при инициализации модулей: `CatalogService.onModuleInit` для справочника и `ScreenSignatureService.onModuleInit` для сигнатур (`apps/api/src/modules/detection/ios/screen-signature.service.ts`). Перечитывание по сигналу теперь реализовано: `POST /api/v1/admin/catalog/reload` вызывает `reload()` ОБОИХ сервисов без перезапуска контейнера — но эндпоинт закрыт `ADMIN_TOKEN` (ADR-025 п.5), и при пустом токене раздел `/admin` недоступен целиком, поэтому на демонстрационном контуре без настроенного токена перезапуск остаётся единственным путём. Измерено на живом контуре обоими способами — тот же запрос с сигнатурой `393×852@3` до наполнения (или до `reload`/перезапуска) отвечал кодом `SCREEN_SIGNATURE_UNKNOWN` и списком из 29 кандидатов, после — `SCREEN_SIGNATURE_MATCHED`, 4 кандидата и адресный вопрос про лоток SIM-карты вместо списка моделей (docs/03 §3.7 п.2, ADR-031). Повторный запрос с `context.region` возвращает `supported` с уверенностью 0,92. То есть без второго и третьего шагов (либо без равноценного им `reload`) не работает не только сужение, но и вся ветка адресного уточнения: у 29 разнородных кандидатов не может совпасть общий уточняющий вопрос, поэтому сервис откатывается к выбору из списка.

**Отдельно от массового наполнения — точечное решение модератора (docs/15 §15.4) применяется НЕМЕДЛЕННО, без этого третьего шага вовсе.** Действия «привязать код», «привязать сигнатуру», «изменить статус eSIM», «добавить псевдоним» и «отметить не телефон» (раздел `/admin`, §15.7) сами перечитывают затронутый кэш внутри одного запроса `POST .../resolve` или `PATCH /admin/devices/{id}` — третий шаг (перезапуск или `/catalog/reload`) нужен ТОЛЬКО когда `devices`/`catalog_overrides` изменены МИМО раздела `/admin` (например, повторным `pnpm seed load` при уже запущенном API).

**Реализация этапа 6.4.** Сервис `web` в `docker-compose.yml` собирается из `apps/web/Dockerfile`
(две стадии: `pnpm --filter @esim-detector/widget... build` и `pnpm --filter @esim-detector/web...
build` в Node, затем статика отдаётся nginx) и слушает порт `8080`, с зависимостью от `api`.
Конфигурация nginx (`apps/web/nginx.conf.template`, подстановка переменных при старте контейнера)
проксирует `/api/` на сервис `api:3000` — демонстрационный React-интерфейс и виджет обращаются к
API через тот же origin, что и сама страница, поэтому базовый сценарий работает независимо от
значения `CORS_ORIGINS` (адрес API — переменная окружения `API_UPSTREAM`, по умолчанию
`http://api:3000`, без файла `.env`; на Render — полный публичный `https://…onrender.com`,
с SNI в TLS, docs/16-deployment.md, дополнение ADR-027). Та же сборка копирует `widget/v1/esim-widget.js` и статическую
страницу-пример (`apps/widget/example/index.html`, этап 6.3) в образ `web`, поэтому оба адреса
выше открываются без отдельного сервиса. Маршрутизация страниц демонстрационного приложения
(`/`, `/debug`, `/admin`) — по `location.pathname` в самом React-коде (`apps/web/src/main.tsx`), без
библиотеки-роутера. nginx (и `vite dev` при локальной разработке) отдают `index.html` на любой путь
без физического файла.

Отдельно предусмотрен режим отладки на стенде: страница `http://localhost:8080/debug` (docs/03
§3.10, ADR-010) позволяет подать произвольный набор сигналов (в текстовом поле в формате поля
`signals` тела запроса `/detect`, включая произвольный `userAgent`) и увидеть полный ответ сервиса
целиком: статус, уверенность, блок `detection` (включая `deviceType`/`method`/`platform`/
`exactModelKnown`), `device`, `candidates[]`, таблицу сработавших `reasons[]`, блок
`clarification` и готовые формулировки `presentation` — а также версию и объём справочника
(`GET /api/v1/catalog/meta`) и `requestId` ответа с возможностью скопировать. Стенд не делает
собственных заключений о статусе eSIM и не доопределяет модель: всё показанное приходит из ответа
API как есть, включая список кандидатов на iOS без «наиболее вероятного» варианта (AGENTS.md,
предметное правило 3). Кнопка «Скопировать запись для signals.golden.json» формирует черновик
записи формата `SignalsGoldenEntry` (docs/08-testing-and-quality.md §8.4,
`tools/eval/src/signals-golden.ts`) из последнего ответа `/detect` и копирует его в буфер обмена;
поле `expected` предзаполнено ответом сервиса, но явно помечено в интерфейсе как черновик,
требующий ручной проверки перед сохранением в `data/fixtures/signals.golden.json`. Категория
выборки предлагается по отправленным сигналам (не по ответу `/detect`) и объясняется подсказкой
под полем; оператор может её сменить. Наполнение самого файла остаётся объёмом другого агента
(ADR-037, ADR-041). Это инструмент для контрольных испытаний: комиссия может воспроизвести любой
кейс своей выборки без реального устройства.

## 7.6а. Публичный стенд на Render

По решению вопроса 5 ([12-open-questions.md](./12-open-questions.md), ADR-025) публичный адрес нужен для проверки комиссией с реального телефона без локального развёртывания. Площадка — Render (render.com). Топология — ADR-027 с дополнением (docs/09-decisions.md): веб отдаётся тем же Docker-образом, что и локально, а не Static Site. Пошаговая инструкция для первого деплоя и обновления — [16-deployment.md](./16-deployment.md).

| Компонент  | Сервис Render           | Источник сборки                                         | Назначение                                                  |
| ---------- | ----------------------- | ------------------------------------------------------- | ----------------------------------------------------------- |
| API        | Web Service             | `apps/api/Dockerfile` (тот же, что у `docker compose`)  | Обслуживает REST API, отдаёт `Accept-CH`, метрики, `/admin` |
| `apps/web` | Web Service             | `apps/web/Dockerfile` (nginx + статика + прокси `/api`) | Демонстрационное приложение, `/debug`, `/admin`, виджет     |
| MongoDB    | Внешний — MongoDB Atlas | —                                                       | Render не предоставляет управляемую MongoDB (ADR-027)       |

Наполнение справочника на Render выполняется тем же образом, что и локально (ADR-015): `tools/seed load`, а следом `tools/seed rebuild-signatures` запускаются отдельным разовым шагом **до** открытия публичного доступа к API, с `MONGODB_URI`, указывающим на кластер Atlas. Обе команды обязательны по той же причине, что и локально (§7.6). Если API уже запущен, после наполнения нужен Restart сервиса либо `POST /api/v1/admin/catalog/reload` за `ADMIN_TOKEN`.

Требования доступа соответствуют решению вопроса 9 (ADR-025): публичные эндпоинты API открыты без ключа, с ограничением частоты (`RATE_LIMIT_RPM`) и списком разрешённых источников (`CORS_ORIGINS` — публичный адрес веб-сервиса, не `*`); раздел `/admin` и эндпоинты модерации закрыты `ADMIN_TOKEN`.

Публичные адреса после выкладки (шаг Ж в [16-deployment.md](./16-deployment.md) §16.5):

| Адрес                                  | Назначение                                              |
| -------------------------------------- | ------------------------------------------------------- |
| https://esimdetector.onrender.com      | Демонстрационное приложение, `/debug`, `/admin`, виджет |
| https://esim-detector-api.onrender.com | API (`/health/ready`, `/api/docs`, `/api/v1/…`)         |

Оба Web Service на бесплатном тарифе **засыпают через 15 минут без входящих запросов**. Пробуждение занимает около минуты: первый запрос после сна не ошибка сервиса. Перед демонстрацией откройте [https://esim-detector-api.onrender.com/health/live](https://esim-detector-api.onrender.com/health/live) и дождитесь `{"status":"ok"}`, затем — адрес приложения. Спящий сервис не тратит бесплатные часы Render (лимит 750 часов в месяц на аккаунт). Как обновлять стенд и что делать, если первый заход обрывается — [16-deployment.md](./16-deployment.md) §16.2, §16.6, §16.8.

## 7.7. Локальная разработка без Docker

```bash
pnpm install
docker compose up -d mongo     # нужна только база
pnpm --filter api seed         # импорт справочника
pnpm dev                       # API и веб-приложение параллельно
```

## 7.8. Настройка

Вся настройка — через переменные окружения. Полный перечень с назначением и значениями по умолчанию — в `.env.example`; ниже — значимые параметры.

| Переменная                         | По умолчанию                 | Назначение                                                                                                                                                                                                                                                     |
| ---------------------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PORT`                             | `3000`                       | Порт API                                                                                                                                                                                                                                                       |
| `MONGODB_URI`                      | `mongodb://mongo:27017/esim` | Строка подключения к базе                                                                                                                                                                                                                                      |
| `NODE_ENV`                         | `production`                 | Режим работы                                                                                                                                                                                                                                                   |
| `CORS_ORIGINS`                     | `*`                          | Разрешённые источники; в промышленной среде задаётся списком                                                                                                                                                                                                   |
| `API_KEYS`                         | пусто                        | Список ключей; при пустом значении проверка ключа отключена                                                                                                                                                                                                    |
| `RATE_LIMIT_RPM`                   | `120`                        | Ограничение частоты запросов на источник; запрос с валидным `X-Admin-Token` (совпал с непустым `ADMIN_TOKEN`) не учитывается (ADR-049, стенд оценки)                                                                                                           |
| `CONFIDENCE_ANSWER_THRESHOLD`      | `0.8`                        | Порог выдачи однозначного ответа                                                                                                                                                                                                                               |
| `CONFIDENCE_GAP_THRESHOLD`         | `0.08`                       | Минимальный разрыв между кандидатами при поиске                                                                                                                                                                                                                |
| `ALLOW_DERIVED_CATALOG_ANSWERS`    | `true`                       | Разрешать ли однозначный ответ по записям уровня `derived` (docs/14 §14.4 шаг 7); выключение сужает ответы до `verified`                                                                                                                                       |
| `ALLOW_UNVERIFIED_CATALOG_ANSWERS` | `false`                      | Разрешать ли однозначный ответ по непроверенным записям справочника                                                                                                                                                                                            |
| `ENABLE_LLM_FALLBACK`              | `false`                      | Зарезервированная точка расширения (интерфейс `QueryNormalizer`, ADR-004); реализации на LLM за флагом нет и не планируется в объёме проекта (решено, [12-open-questions.md](./12-open-questions.md), вопрос 6) — переключение флага в `true` не имеет эффекта |
| `ADMIN_TOKEN`                      | пусто                        | Токен доступа к разделу модерации; при пустом значении раздел закрыт                                                                                                                                                                                           |
| `LOG_LEVEL`                        | `info`                       | Уровень журналирования                                                                                                                                                                                                                                         |
| `RESOLUTION_LOG_TTL_DAYS`          | `30`                         | Срок хранения журнала резолюций                                                                                                                                                                                                                                |

Переменной окружения для тестовой базы данных нет намеренно: тесты поднимают собственный изолированный экземпляр MongoDB и игнорируют `MONGODB_URI`. Это исключает сценарий, при котором забытое значение переменной приводит к работе тестов на данных приложения ([08-testing-and-quality.md](./08-testing-and-quality.md), раздел 8.5).

### Переменная сборки виджета

Таблица выше — переменные окружения API (`.env.example`, читаются в момент выполнения контейнера). Сборка виджета (`pnpm --filter @esim-detector/widget build`, `apps/widget/vite.config.mts`) добавляет к ним ОТДЕЛЬНУЮ переменную сборки, читаемую самим Vite во время `vite build`, а не приложением в рантайме — поэтому она не входит в `.env.example`:

| Переменная             | По умолчанию | Назначение                                                                                                                                                                                                                                 |
| ---------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `VITE_WIDGET_API_BASE` | пусто        | Запасной адрес API (без версионированного пути, см. §7.2), вкомпилированный в `widget/v1/esim-widget.js` на случай, если тег `<script>` подключения не указал `data-api-base`. `data-api-base` тега всегда в приоритете (ADR-027, ADR-040) |

Значение читается через `vite.config.ts` (`loadEnv`) и заменяет буквальный идентификатор `__ESIM_WIDGET_API_BASE__` в собранном файле — не через `import.meta.env`, чтобы не требовать ESM-транспиляции для тестов (`apps/widget/src/web-component/global.d.ts`, `resolve-api-base.ts`).

Пороги уверенности вынесены в конфигурацию сознательно: они задают баланс между долей автоматических ответов и риском ошибки, и это решение бизнеса заказчика, а не разработчика.
